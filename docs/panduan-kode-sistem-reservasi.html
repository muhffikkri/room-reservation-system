02 / Cara kerja

Satu request dari ujung ke ujung

Gunakan pola ini saat membaca fitur apa pun: mulai dari route, ikuti middleware, lihat controller, lalu cari service dan model yang disentuh.

1. Route menerima URL dan methodContoh: PATCH /admin/pengguna/{user}/verifikasi diarahkan ke AccountVerificationController@verify.
2. Middleware menyaring requestauth memastikan sudah login, active memastikan status akun aktif, role:admin memastikan role admin.
3. Route model binding mengisi model{user} berubah menjadi instance User. Jika ID tidak ada, Laravel memberi 404.
4. Controller menjadi adapter tipisController meneruskan model dan actor ke service, menangkap conflict, lalu membuat redirect + flash message.
5. Service mengubah state dengan amanService membuka transaksi, mengunci baris bila perlu, memeriksa status/role, mengubah data, dan mencatat audit.
6. Response kembali ke BladeView membaca data baru dan menampilkan status sukses/error. Test feature memverifikasi hasil yang terlihat user.
Bukti: kelompok route admin dan pemisahan middlewareroutes/web.php · L67–113
Route::middleware(['auth', 'active', 'role:admin'])
    ->prefix('admin')->group(function (): void {
    Route::patch('/pengguna/{user}/verifikasi', [
        AccountVerificationController::class, 'verify'
    ])->name('admin.pengguna.verify');
});

03 / Fondasi akses

Auth & akun

Auth custom memakai session guard Laravel. Admin verification bukan email verification: status akun ditentukan sistem oleh admin.

Registrasi mandiri

  1. Input email, identity, dan phone dinormalisasi.
  2. Server memvalidasi format, panjang, dan keunikan.
  3. Field role/status dari request diabaikan.
  4. Akun selalu dibuat sebagai pengguna + pending.
  5. User diarahkan ke login, tetapi belum bisa masuk.

Verifikasi akun

AccountVerificationController hanya mengatur redirect. Aturan berada di AccountVerificationService: lock target, pastikan role pengguna, pastikan pending, ubah status, dan tulis actor/waktu.

Verifikasi vs restore: verify mengubah pending → aktif; reject mengubah pending → ditolak; restore mengubah ditolak → pending. Restore tidak memberi akses login sebelum admin melakukan verify lagi.

10 / Guardrail

Validasi & business rules

Validasi bentuk input berada di FormRequest. Validasi yang membutuhkan state database dan transaksi berada di Service atau Rule object.

FormRequest

  • AdminAccountRequest: name, email, password confirmed, identity, phone.
  • StoreReservationRequest: date, waktu, purpose, facility ID.
  • StoreReportRequest: kategori, deskripsi, foto nullable/image/max 2 MB.
  • UpdateReportStatusRequest: status dan catatan untuk status akhir.

Client-side validation hanya membantu UX; server tetap sumber kebenaran.

Rule reservasi

  • SlotTimeValid: rentang 07.00–20.00, interval 30 menit, maksimal 4 jam.
  • BookingLeadTime: mulai minimal 30 menit dari sekarang.
  • FacilityBookable: fasilitas harus aktif.
  • PendingQuota: kuota pending harian user.
  • NoApprovedOverlap: tidak bentrok dengan approved.

11 / Permukaan UI

View, layout, dan JavaScript

Blade memetakan domain ke halaman. Layout membaca role untuk menampilkan menu yang sesuai, tetapi keamanan sebenarnya tetap berada di route middleware.

Layout utama

resources/views/layouts/app.blade.php memuat Vite assets, navbar responsive, flash message, dan menu berbeda untuk pengguna, petugas, dan admin.

Class active memakai request route sehingga highlight menu mengikuti route yang sedang tampil.

Komponen reusable

resources/views/components/ui/ berisi card, badge, select, table. components/reservation/slot-picker.blade.php mengisolasi picker slot.

JavaScript

resources/js/app.js menangani dialog konfirmasi, preview file foto, mobile menu, dan tab/jadwal sesuai kebutuhan UI.

CSS & bundling

resources/css/app.css adalah entry Tailwind. Vite membangun asset ke public build. Saat perubahan UI tidak terlihat, jalankan npm run build atau npm run dev.

Bedakan UX dan security: menu admin yang disembunyikan dari petugas hanya UX. Request manual ke URL tetap harus ditolak oleh middleware/policy; itulah alasan test route isolation lebih penting daripada sekadar mengecek menu.

14 / Metode belajar

Urutan membaca yang paling masuk akal

Jangan mulai dari semua file sekaligus. Pilih satu alur kecil, telusuri sampai database, lalu ulangi dengan modul lain.

Rute belajar 1 — login

  1. Baca routes/web.php bagian guest.
  2. Baca LoginController.
  3. Ikuti AccountStatusGate.
  4. Lihat User dan config auth/session.
  5. Buka AuthFlowTest.

Rute belajar 2 — verify

  1. Mulai dari route PATCH admin.
  2. Lihat controller hanya redirect.
  3. Telusuri service: lock, guard role, status, update.
  4. Ikuti observer session.
  5. Bandingkan snapshot users dengan audit actions.

Rute belajar 3 — approve

  1. Baca FormRequest officer.
  2. Ikuti ReservationService::approve.
  3. Pahami lockForUpdate dan overlap.
  4. Lihat actor decided_by/at.
  5. Baca test approval dan overlap.
Teknik tracing: untuk setiap method, catat empat hal: input, guard/validasi, perubahan state, dan response. Jika salah satu tidak jelas, cari file yang dipanggil method tersebut—bukan langsung menambah kode baru.
