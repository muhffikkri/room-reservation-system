1. Ringkasan Eksekutif

Fondasi keamanan repo ini baik: tidak ditemukan celah Critical (RCE, SQL injection tereksploitasi, auth-bypass, IDOR reservasi/laporan, CSRF hilang, upload PHP/SVG). Password di-hash, sesi diregenerasi, CSRF ada di semua form, query memakai binding, XSSStored mayoritas ter-escape, overlap dikunci transaksi, verifikasi akun memakai lock+audit, dan sesi dibatalkan saat role/status berubah.

5. Detail Temuan

A1 — Stored XSS konteks-JS di onsubmit halaman admin fasilitas Medium

OWASP A03 Injection • resources/views/admin/fasilitas/index.blade.php:111 • sumber: FacilityRequest.php:33 (name max:120)

<form method="POST" action=".../nonaktifkan"
      onsubmit="return confirm('Fasilitas {{ $facility->name }} akan dinonaktifkan ...')">

{{ }} memakai htmlspecialchars(ENT_QUOTES) — aman untuk konteks HTML, tidak cukup untuk string JS dalam atribut. Parser HTML men-decode entitas (&#039; → ') sebelum JS dieksekusi, sehingga nama seperti x');alert(document.cookie);// (muat dalam 120 karakter) memutus string confirm('...'). Prasyarat: pelaku sudah ber-role admin (pembuat fasilitas, FacilityRequest::authorize membatasi ke admin) — dampaknya serangan intra-admin (pencurian sesi/CSRF) saat admin lain membuka daftar fasilitas.

Rekomendasi: jangan interpolasi ke inline JS. Pakai data-* + listener, mis. <form data-name="{{ $facility->name }}" class="js-deactivate"> lalu confirm(el.dataset.name); atau @json($facility->name). Kontras: confirm() statis di petugas/laporan/show:169,179, admin/pengguna/index:39, verifikasi:41 sudah aman.

A2 — Bypass kuota 2 pending/hari via race condition Medium

OWASP A04 Insecure Design • app/Services/ReservationService.php:35-60 • app/Rules/PendingQuota.php:23-30 • BR-4

// Validasi kuota BERADA DI LUAR transaksi:
Validator::make([... new PendingQuota($user->id, $start) ...])->validate(); // count() tanpa lock
return DB::transaction(function () {
    $conflict = Reservation::approved()->overlap(...)->lockForUpdate()->exists(); // hanya overlap dicek ulang
    ...
});

Tiga request paralel saat count=1 semuanya lolos validasi lalu masuk transaksi — kuota tidak pernah dihitung ulang dengan lock. Hasil: 3–4 pending di hari yang sama (spam antrean, beban petugas). Overlap justru sudah benar polanya (cek ulang + lockForUpdate di create:53-60 dan approve:86-111) — kuota belum meniru pola itu.

Rekomendasi: hitung ulang kuota di dalam transaksi dengan lockForUpdate() (atau kunci logis per user+tanggal), atau tegakkan via constraint DB + tangani 409. Uji dengan 3 POST paralel saat kuota tersisa 1.

A3 — Cookie sesi tanpa Secure, sesi tak terenkripsi, APP_URL http Medium*

OWASP A02/A05 • config/session.php:50 ('encrypt' => env SESSION_ENCRYPT false), :172 ('secure' => env SESSION_SECURE_COOKIE) • .env: SESSION_SECURE_COOKIE unset, SESSION_ENCRYPT=false, APP_URL=http://localhost:8000

Default http_only=true dan same_site=lax sudah baik (anti akses JS + mitigasi CSRF dasar). Namun tanpa Secure + via http, cookie sesi bisa disadap di jaringan tak tepercaya; tanpa enkripsi, payload sesi DB/file lebih mudah dibaca bila storage bocor. Di lokal ini wajar; wajib diubah saat demo publik/produksi (https).

Rekomendasi produksi: SESSION_SECURE_COOKIE=true, pertimbangkan SESSION_ENCRYPT=true, APP_URL=https://.... Jangan set Secure saat masih http-lokal (cookie tak terkirim).

A4 — APP_DEBUG=true + LOG_LEVEL=debug Medium*

OWASP A05/A09 • .env:4 (APP_DEBUG=true), .env:21 (LOG_LEVEL=debug) • config/app.php:42

Debug aktif menampilkan stack trace + path absolut (D:/Praktikum/... terlihat di storage/logs/laravel.log) ke browser saat error — membocorkan struktur app, versi, query. Cocok untuk dev, berbahaya bila file .env ini terbawa ke server demo/produksi.

Rekomendasi: produksi/demo publik wajib APP_DEBUG=false, LOG_LEVEL=warning|error. Verifikasi dengan memicu 404/500 dan pastikan halaman error generik.

A5 — Foto laporan/fasilitas publik tanpa kontrol akses Low

OWASP A01 • ReportService.php:30-32 (store 'reports','public') • Admin/FacilityController.php:125-132 • config/filesystems.php:41-48 • view laporan/show:54, petugas/laporan/show:63, admin/fasilitas/index:59

Nama file acak (hashName()) sehingga tak bisa ditebak — mitigasi parsial yang baik. Tetapi siapa pun pemegang URL /storage/... bisa GET tanpa auth/Gate; URL bisa bocor via log/referer/share. Foto laporan bisa sensitif (kerusakan + lokasi).

Rekomendasi: putuskan klasifikasi: bila sensitif → pindah ke disk local + route unduh ber-Gate (atau signed URL sementara); bila memang publik → dokumentasikan sebagai keputusan sadar.

A6 — $fillable over-permissive Low (defense-in-depth)

OWASP A01 • User.php:15 (role, account_status, verified_by/at, rejected_by/at) • Reservation.php:12 (user_id, status, decided_by...) • Report.php:13 (status, handled_by...)

Saat ini aman: RegisterController:51-59 memaksa role=pengguna,status=pending; BaseAccountController:60-68 memaksa role+status server-side; ReservationService:62-69 dan ReportService:34-41 set user_id/status dari objek. Risikonya ke depan: satu $request->all()/`create($validated)` lalai = eskalasi role/status.

Rekomendasi: keluarkan kolom otorisasi dari $fillable (set via forceFill/service), atau pertahankan dengan komentar penjaga + test mass-assignment (POST /register dengan role=admin harus tetap pengguna/pending).

A7 — Tanpa throttle di endpoint tulis Low

OWASP A07 • routes/web.php:30,33 (hanya login/register throttle:10,1) vs :41 (reservasi.store), :47 (laporan.store), :59-64 (petugas.*), :82-110 (admin.*) tanpa throttle

Login sudah berlapis baik: middleware throttle:10,1 + RateLimiter 5/menit per email|IP (LoginController:38-46). Endpoint tulis tanpa batas mempermudah spam reservasi/laporan (menguatkan A2) dan enumerasi facility_id.

Rekomendasi: tambah throttle wajar mis. throttle:30,1 untuk reservasi.store/laporan.store dan aksi petugas/admin.

A8 — Wildcard LIKE tanpa escape + filter tanpa allowlist/batas Low

OWASP A04 • Admin/FacilityController.php:24,28 ("%{$keyword}%") • ReservationController.php:39-43 (status tanpa in:) • Facility.php:43-47 (scopeSearch)

Parameter ter-binding (aman dari SQLi — terbukti tak ada DB::raw/whereRaw berisi input user; satu-satunya orderByRaw/selectRaw bersifat statis) dan output ter-escape (value="{{ $keyword }}"). Namun %/_ dari user berfungsi sebagai wildcard (match-all / query berat), q admin tanpa max, dan status riwayat pengguna tanpa allowlist (vs versi petugas Officer/ReservationController:36-39 yang sudah in:... — bagus).

Rekomendasi: samakan dengan FacilityController (publik):54-65 — q max:100, escape via addcslashes($keyword,'%_\\'), status Rule::in([...]).

A9 — Otorisasi andalkan middleware saja Low

OWASP A01 • UpdateReportStatusRequest.php:15-17 (hanya user()!==null) • Officer/ReservationController.php:56-79 (tanpa Gate) • StoreReservation/StoreReportRequest::authorize tanpa cek role

Aman selama grup route tak berubah (role:petugas/admin/pengguna di routes/web.php:36,51,67 + EnsureRole:25-27 strict). Sekali route salah pasang, endpoint mutasi terbuka lintas role. Inkonsistensi: Reject/Cancel*Request:21 membolehkan isPetugas||isAdmin padahal middleware role:petugas menolak admin — dead-code yang membingungkan. Kontras baik: FacilityRequest:22 dan AdminAccountRequest:27 sudah cek role di authorize(); Officer/ReportController:show:52, ReservationController:show:114, ReportController:show:58 sudah Gate::authorize('view').

Rekomendasi: tambahkan cek role di UpdateReportStatusRequest::authorize() (+ Store*Request) dan Gate::authorize di aksi officer sebagai kunci kedua yang murah.

A10 — Security headers hilang Low

OWASP A05 • bootstrap/app.php (tanpa middleware header kustom) • docker/nginx/default.conf (hanya deny /\.ht, tanpa X-Frame-Options/CSP/HSTS/X-Content-Type-Options/Referrer-Policy) • tanpa config/cors.php

Aplikasi rentan clickjacking (tidak ada X-Frame-Options/DENY atau frame-ancestors) dan MIME-sniffing; HSTS tak relevan selama http. Risiko clickjacking nyata untuk aksi POST (approve/reject) bila admin/petugas dibujuk membuka halaman jebakan — sebagian termitigasi oleh SameSite=lax + CSRF token.

Rekomendasi produksi: tambah header via middleware/nginx: X-Frame-Options: DENY (atau CSP frame-ancestors 'none'), X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, dan HSTS setelah https aktif.

A11 — Inkonsistensi panjang cancel_reason Info

ReservationController.php:130-135 (min:5) vs RejectReservationRequest.php:32 / CancelReservationOfficerRequest.php:32 (min:10) • view reservasi/show:148 (minlength=5)

Bukan lubang (server tetap enforce), tapi drift aturan BR-8/BR-9 menyulitkan audit dan pengujian.

A12 — Enumerasi akun via pesan validasi Info

RegisterController.php:44-48, AdminAccountRequest.php:39-45 (unique email/identity/phone)

Login sudah baik (pesan generik "Email atau password salah", LoginController:51-53). Pendaftaran/admin-create wajar membocorkan keberadaan email/identitas via pesan unique — standar industri, diterima. Flash "Akun {email} berhasil..." di area admin hanya terlihat admin.

A13 — Invalidasi sesi hanya driver database Info

app/Observers/UserObserver.php:18-34 (terdaftar di AppServiceProvider.php:24) • .env:30 SESSION_DRIVER=database

Implementasi sudah memenuhi spec §5.2 untuk konfigurasi saat ini: hapus baris sessions + null-kan remember_token saat role/account_status berubah, plus EnsureAccountActive menendang sesi basi di request berikutnya dan LoginController:62-70 menolak pending/ditolak + membersihkan token. Bila driver diganti ke file, invalidasi menyeluruh tak berlaku (sudah didokumentasikan di komentar kode).

A14 — Tanpa alur reset password Info

database/migrations/0001_01_01_000000_create_users_table.php:24-29 (password_reset_tokens) • routes/web.php nihil route reset

Tidak ada rute lupa/reset password — pemulihan akun hanya via admin. Bukan celah, tapi risiko ketersediaan/UX + godaan reset manual via DB.

A15 — Higiene secret lokal Info (positif + catatan)

.env (APP_KEY terisi, DB root + password dev lemah — disensor) • .gitignore:48 (.env diabaikan) • git ls-files: hanya .env.example terlacak; git log --all -- .env kosong • .dockerignore:5-6 mengecualikan .env dari image

Tidak ada secret ter-commit — baik. Catatan: password DB dev lemah untuk akun root (dapat diterima di laptop dev, wajib diganti di server bersama/produksi; bedakan kredensial per lingkungan via DB_PASSWORD/DB_ROOT_PASSWORD di docker-compose.yml). File report-code-main.html tak terlacak di root — periksa isinya sebelum commit.
